API key scopes control which REST API operations an integration can perform. Each key has one access level, and higher levels include the access of lower ones. Choose the lowest level the integration needs, then optionally restrict the key to a Task allowlist.

Create and manage keys from **Settings > API Keys**. See [Get Your Figranium API Key](/api-key) for the creation flow and authentication examples.

## Available scopes

| Access level | Scope | Access |
| :-- | :-- | :-- |
| **Read tasks** | `tasks:read` | View Tasks. |
| **Run tasks** | `tasks:run` | View and run Tasks, and read their execution results. |
| **Manage tasks** | `tasks:manage` | View, run, create, edit, and delete Tasks, plus access browser, credential, Cabinet, capture, and screenshot routes. |

Choose a scope based on the integration's responsibility:

- Use `tasks:read` for dashboards or tools that only need to inspect Task definitions.
- Use `tasks:run` for jobs that trigger Tasks and collect their results.
- Use `tasks:manage` for systems that create, update, or delete Tasks, or that need browser, credential, Cabinet, capture, or screenshot access.

## MCP and common integrations

### MCP clients

For the Figranium MCP server, use `tasks:manage` when you want the connected AI client to use the full MCP toolset. Figranium's MCP integration can create and manage Tasks, execute them, inspect execution history, manage schedules, and work with Cabinets.

If your MCP client should only run existing Tasks and inspect their results, use `tasks:run` instead. Use `tasks:read` for a read-only MCP connection that only lists or inspects Tasks. In every case, add a Task allowlist when the client should be limited to specific Tasks.

See [MCP Integration](/mcp-integration) for client setup and available tools.

### Other common uses

| Use case | Recommended scope |
| :-- | :-- |
| Read-only dashboard or Task catalog | `tasks:read` |
| Scheduled job, webhook, or script that triggers Tasks | `tasks:run` |
| Integration that runs Tasks and reads execution results | `tasks:run` |
| Admin tool that creates, edits, or deletes Tasks | `tasks:manage` |
| Tool that opens the browser, reads captures or screenshots, or works with Cabinets | `tasks:manage` |
| Full-featured MCP client | `tasks:manage` |

## Task allowlists

A Task allowlist narrows a key's access to selected Tasks. A restricted key cannot access other Tasks, even when its scope would otherwise allow it. The allowlist is enforced on every Task operation, including full Task saves.

Use an allowlist when an integration only needs to run one workflow or manage a small set of workflows. Leave the allowlist unrestricted only when the integration genuinely needs access to every Task permitted by its scope.

<Warning>
  Scopes and Task restrictions work together. A key must have both the required scope and access to the requested Task.
</Warning>

## Choosing scopes for common REST API operations

| Operation | Minimum scope |
| :-- | :-- |
| List or inspect Tasks | `tasks:read` |
| Trigger a Task with `POST /api/tasks/:id/api` | `tasks:run` |
| Read execution results | `tasks:run` |
| Create, update, or delete a Task | `tasks:manage` |
| Open the browser or use the inspector highlight | `tasks:manage` |
| List or create Cabinets, or download Cabinet items | `tasks:manage` |
| Read captures or screenshots | `tasks:manage` |

When a key runs a Task with `POST /api/tasks/:id/api`, the request cannot override the Task's `extractionScript`. Requests that include it return `400 EXTRACTION_SCRIPT_OVERRIDE_FORBIDDEN`.

The exact endpoint behavior is documented in the [REST API Reference](/rest-api). Health and capabilities endpoints are available for checking server status and supported features.

## Recommended setup

1. Create one named API key per integration or workflow.
2. Select the lowest access level that satisfies the integration.
3. Restrict the key to the required Tasks when possible.
4. Store the secret securely and rotate or revoke it if exposed.
